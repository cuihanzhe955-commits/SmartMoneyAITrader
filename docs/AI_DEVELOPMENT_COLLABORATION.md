# 开发与交付规范

> 适用项目：Smart Money AI Trader  
> 目的：保持工程可维护、交付可审查，避免重复开发、并行冲突和未经授权的高风险改动。

## 1. 基本原则

1. 当前 GitHub main 是远端共享基线；本机运行目录、历史工作树和备份可能包含尚未同步的资料，不能仅凭目录名称判断版本。
2. 一个任务、一个写入者、一个工作分支。不得让多个开发过程同时修改同一工作树或相同文件。
3. 先检查现有源码、调用方、测试、配置、数据库结构和打包白名单，再决定修改方案。
4. 先评估成熟开源实现；能安全复用就不重复开发，但必须检查许可证、维护状态、Windows 兼容性、依赖和回滚。
5. 模拟、Mock、历史回放和公开只读数据不能冒充平台联调或真实账户验收。
6. 产品所有者保留产品范围、生产依赖、数据库迁移、删除、账户权限、真实交易和发布的最终决定权。

## 2. 任务开始前

- 核对远端 main、当前分支、HEAD、工作区状态和未跟踪文件。
- 检查所有相关工作树、备份和本地运行目录；不要假设它们等于远端 main。
- 阅读 README、主计划、项目进度及任务相关阶段报告。
- 明确任务目标、允许修改路径、禁止触碰路径、验收标准和测试命令。
- 检查是否已有未合并变更或其他写入者正在工作。

发现本地修改、未知文件、数据库或工作树归属不清时，先停止并报告，不得 reset、clean、覆盖或删除。

## 3. 分支和交接

- 从确认后的远端基线创建独立分支；禁止直接在 main 开发。
- 每个分支只处理一个可审查目标，不混入无关重构。
- 交接前由当前写入者停止修改，提供最后 commit、文件差异、测试结果、未完成事项和回滚点。
- 后续写入者只能在确认前一位已停止后接手。
- PR 由项目所有者审核和合并；不得自行合并或强制改写共享历史。

## 4. 开源项目采用流程

1. 搜索 GitHub 上的候选项目和已有实现。
2. 检查 README、LICENSE、NOTICE、具体 commit、维护活跃度、安全公告和依赖树。
3. 评估 Python/Node/Windows 兼容性、架构重叠、数据契约和性能。
4. 先做隔离 POC，不直接替换生产模块。
5. 补充接口适配、回归、依赖锁定和回滚说明。
6. 记录采用、不采用或延后的理由。

许可证不清楚或与项目分发方式存在潜在冲突时，不复制代码，先完成合规评估。

## 5. 测试与交付

每次交付提供：
- 修改文件及原因；
- 实际命令、运行环境和 commit；
- 通过/失败/跳过数量；
- 未执行测试及原因；
- 已知风险和回滚点；
- 文档同步情况。

根据影响范围运行 Python 定向/全量测试、前端类型检查与构建、浏览器测试、Windows 启停、数据库迁移和依赖审计。退出码为 0 但日志有未解释异常，仍不能判定通过。

## 6. 安全与数据边界

- 不提交 API Key、Secret、私钥、助记词、Cookie、访问令牌或真实账户凭据。
- 不上传个人交易流水、账户余额、私人数据库、身份信息或本机日志。
- 不擅自删除用户数据、重置数据库、覆盖备份或清理未知文件。
- 默认使用合成数据、历史数据、隔离模拟环境和最小权限。
- 不绕过交易所地区、产品或账户资格限制。
- AI 建议不能绕过确定性风控；任何真实资金操作必须有独立明确授权。

## 7. 版本状态

必须分别标注：已规划、已实现、离线测试通过、平台联调通过、真实账户验收通过。不能把计划、局部测试或模拟成绩写成已交付的真实交易能力。
